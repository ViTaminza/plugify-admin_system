# admin_system — Plugify API design

The admin core of the Pisex `cs2-admin_system` Metamod:Source plugin, ported to a Plugify C++
plugin. This document is the contract between the plugin (`plugins/admin_system`) and the
modules that used to talk to it through the `IAdminApi` interface of
`ref/pisex/cs2-admin_system/include/admin.h`.

Phase 1 (this document): the API design — the manifest, the generated consumer headers, the
hand-written consumer wrapper `include/admin_api.hpp` and the engine-free core
(`admin_core`: configuration, schema, admin loading, permissions, punishments).
Phase 2 adds the engine glue (`src/plugin.cpp`: s2sdk listeners, commands, chat, menus, player
lookups) on top of `admin_core` and `libs/pisexcompat`.

## 1. Files

| Path | Role |
| --- | --- |

`plugify-gen` custom target runs when the manifest is newer; a missing generator is ignored and
the checked-in headers are used).

## 2. Boundary rules

1. **Types.** Only `plg::string`, `plg::vector<plg::string>`, `int32`, `int64`, `bool`, `float`
   and plain C function pointers cross the plugin boundary. No `std::function`, no captures, no
   C++ classes, no exceptions.
2. **`std::string&` out-parameters become `plg::string&`** with `"ref": true` in the manifest
   (the display callbacks of `RegisterCategory` / `RegisterItem` are the only ones).
3. **`SourceMM::PluginId` registration becomes a Register/Unregister pair.** The original keyed
   its listeners by plugin id, i.e. one listener per plugin, re-registering replaced it; the
   Plugify pairs keep that: registering the same function pointer again replaces the previous
   registration, `*_Unregister` removes it (idempotent). The consumer wrapper hides this
   completely - a module calls `OnCoreLoaded(cb)` / `OnCoreLoadedUnregister()`.
4. **`GetMySQLConnection()` becomes `GetDatabaseConfig()`.** A Plugify plugin cannot share
   another plugin's `Database` object (the worker thread and the callback queue belong to the
   owner), so the *settings* are exported and every plugin opens its own plgdb connection.
5. **`const char*` returns become `plg::string`.** The wrapper converts them back to `const char*`
   pointers that are as long-lived as the original's were (see §5).
6. **No exceptions** escape into the engine: every trampoline of the wrapper and every exported
   function of phase 2 catches (`catch (...)` + log).
7. **Timestamps are `int64`.** The original kept unix times in `int` (per-slot arrays and
   `INT` columns); the API widens the *returned* values so a 2038 wraparound cannot happen, the
   columns keep the original `INT` type so both variants share one database.

## 5. Using the API from a module

Include paths (module `CMakeLists.txt`):

```cmake
target_include_directories(my_module SYSTEM PRIVATE
        "${CMAKE_SOURCE_DIR}/plugins/admin_system/include"                            # admin_api.hpp
        "${CMAKE_SOURCE_DIR}/plugins/admin_system/include/external/plugify/include"   # generated
        "${CMAKE_SOURCE_DIR}/sdk/include")
target_sources(my_module PRIVATE
        "${CMAKE_SOURCE_DIR}/plugins/admin_system/include/external/plugify/include/admin_system/admin_system.cpp")
```

Porting recipe:

```cpp
// before (Metamod)
#include "include/admin.h"
IAdminApi* g_pAdminApi;
g_pAdminApi = (IAdminApi*)g_SMAPI->MetaFactory(Admin_INTERFACE, &ret, NULL);
g_pAdminApi->OnCoreLoaded(g_PLID, []{ ... });

// after (Plugify)
#include <admin_api.hpp>
admin_system::AdminApi* g_pAdminApi = &admin_system::AdminApi::Get();
g_pAdminApi->OnCoreLoaded([]{ ... });                    // the plugin id argument is gone
g_pAdminApi->RegisterItem("ban", "Item_Ban", "players", "@admin/ban", nullptr, OnItemSelect);
```

Everything else keeps its original spelling: `HasPermission(iSlot, "@admin/ban")`,
`GetTranslation("Item_Ban")`, `AddPlayerPunishment(i, RT_BAN, 3600, r, admin)` (with the same
default arguments: `adminID = -1`, `notify = true`, `db = true`), `GetAdminFlags(i)` returning
`std::vector<std::string>`, `RT_BAN/RT_MUTE/RT_GAG/RT_SILENCE` as `admin_system::RT_*`.

Lifetime rules of the `const char*` getters (identical to the original's maps):
`GetTranslation`, `GetFlagName`, `GetAdminName`, `GetAdminGroupName` and
`GetPlayerPunishmentReason` return pointers into a per-plugin cache that stays valid until the
same key/slot is queried again (translations survive until `ReloadTranslations()`), and the
`category`/`identity` pointers handed to the menu callbacks point into the registration map
(the original handed out `Item::szIdentity` the same way).

Callbacks must not throw: the trampolines catch and log through `plg::Log`.

Database: a module that needs its own queries (e.g. CheckCheats writing `checkcheats_stats`):

```cpp
const admin_system::DatabaseConfig db = g_pAdminApi->GetDatabaseConfig();
auto connection = plgdb::Database::Create(admin_system::MakeDatabaseConfig(db, "admin.sqlite3"));
```

## 7. The engine-free core (`admin_core`)

`admin_core` is a static library (plgdb only, no s2sdk, no Plugify types) so the whole
database/permission/punishment logic is unit-testable and phase 2 stays glue:

* **`Config`** — the `core.ini` model with the semantics of `LoadConfig()`: `database_prefix`,
  `admin_server_id`, `punish_server_id`, `punish_ip`, `time_reason_type`, `ban_delay`,
  `notify_type`, `unpunish_type`, `immunity_type`, `punish_offline_count`,
  `unpunish_offline_count`, `static_name`, `message_type`, `own_reason`,
  `mute_ignore_commands`, `default_permissions`, the `flags` map (name + `access` list), and the
  `reasons` / `times` / `times_reasons` tables of the punishment menus. The defaults are the
  values of the shipped file (`ref/pisex/live-configs-admin_system/core.ini`); phase 2 fills the
  struct from the `.ini` with the pisexcompat KeyValues parser. `database_prefix` is validated
  (plain identifier, ≤ 32 chars) because it is interpolated into SQL.
* **Schema** — byte for byte the `CREATE TABLE` statements of `database.cpp` for
  `{prefix}groups`, `{prefix}admins`, `{prefix}admins_servers`, `{prefix}punishments`
  (only `AUTO_INCREMENT` / `AUTOINCREMENT` differs per driver) plus the reserved console row
  (`as_admins.id = 1`, `steamid = '0'`). Blocking (`QuerySync`), startup only, first failure
  throws → the plugin logs it and fails soft.
* **Admin loading** — `LoadAdmin(slot, steamid, player_name)` runs the joined
  `admins / admins_servers / groups` SELECT of `CheckPermissions()`, and
  `ComputeAdminRecord()` reproduces its rules, quirks included:
  flags accumulate over every row that passes the `admin_server_id` filter (`-1` = every
  server), the `flags` block of `core.ini` expands them into permissions, immunity is the
  maximum of `admins_servers.immunity` and `groups.immunity` - with the original's ordering
  quirk that the *row* immunity is folded in **before** the server filter, the group immunity
  after it - `expires` keeps the largest value and `0` (permanent) wins over everything but
  `0`, a `NULL` name falls back to the player name, and only a found row fires
  `onAdminLoaded` (= `OnAdminConnectedSend`). Loads are asynchronous and are discarded when the
  slot is reset (`ResetSlot`) while the query is in flight.
* **Permissions** — `HasPermission` (with `default_permissions` and `@admin/root`),
  `HasFlag`, `IsAdmin`, and the `AddPlayerLocal*` / `RemovePlayerLocal*` in-memory changes of
  the VIP modules. Console (`-1`) always passes.
* **Punishments** — `Punish` / `PunishOffline` (pre-hook veto, `INSERT` with the original
  columns, in-memory state, post hook), `TryPunish` / `TryPunishOffline` (the `immunity_type`
  rules in front; the offline variant reads the target's immunity from the database like the
  original), `Unpunish` / `TryUnpunish` / `UnpunishOffline`, `LoadPunishments` (connect:
  expired rows and other servers are skipped, a ban only asks the caller to disconnect - the
  original never stored bans in memory) and `ReloadPunishments` (forced: reports every active
  punishment and lets the caller apply `ban_delay`). `MergeExpiry` keeps the original's
  `current != 0 && current < incoming` rule verbatim. `ExpireState()` is the per-second timer
  that forgets expired punishments and admin rights and reports what the plugin has to announce.
* **Maintenance** — `AddAdmin` (reuse the `as_admins` row, `INSERT IGNORE` the
  `admins_servers` row for this server, reload the rights of an online target, `bDB = false` =
  in-memory only), `RemoveAdmin` (delete this server's row, drop the shared `as_admins` row when
  no server uses it any more, clear the online records), `AddGroup`, `RemoveGroup`,
  `RemoveExpiredAdmins`.
* **Engine boundary** — the core never asks the engine anything: the plugin sets
  `findOnlineSlots` (steamid → slots) and passes a `PlayerIdentity` (slot, steamid64, name, ip)
  into `Punish`/`TryPunish`; everything else comes back through the hooks
  (`onAdminLoaded`, `onPunishmentsLoaded`, `onPlayerPunish`, `onOfflinePlayerPunish`,
  `onPlayerUnpunish`, `onOfflinePlayerUnpunish`, the two `*Pre` vetoes and `onError`).

Threading: `Query()` never blocks (plgdb worker thread), all callbacks run on the game thread
from `Poll()`, `CreateSchema()` is the only blocking statement. Results that land after the
core was destroyed are dropped (a lifetime token guards every callback).

### Compatibility notes (deliberate deviations)

* The online unpunish check of the original was disabled by an inverted condition
  (`if (iAdminID != -1) bUnpunishAll = true;`); here the documented `unpunish_type = 0` rule
  ("only the admin that issued the punishment, unless it has `@admin/unpunish_all`, or the
  console") is applied to the online path exactly as the original applied it to the offline one
  and to its menus.
* `g_pAdmins[-1]` of the original (console) is never indexed; the console always passes
  permission and immunity checks.
* Every slot starts without a punishment (`-1`); the original's arrays started at `0`, which
  reported "punished" before the first load.
* `expires`/`created` timestamps are `int64` in memory and in the API (the columns stay `INT`
  for Metamod compatibility).
* The in-memory "punishments of a player" of an offline-only target are not tracked (the
  original only tracked connected players, its `g_mOfflineUsers` list is a menu feature of
  phase 2).
* `RemoveOfflinePlayerPunishment` runs the `UPDATE` directly (the original ran the same query
  as a `SELECT` first to decide whether to run it).

## 8. The engine side (phase 2)

`src/plugin.cpp` (lifecycle, config/phrases/database, s2sdk listeners, reconcile, the core hooks,
the notifications and the 60 exports), `src/commands.cpp` (the commands) and `src/menus.cpp` (the
admin menu) port `admin_system.cpp` + `menus.cpp` onto admin_core + pisexcompat. `package.sh` lays
out the ready-to-drop package (configs from `ref/pisex/live-configs-admin_system`, phrases from
`ref/pisex/live-translations`, the manifest, the `.so` and a `databases.cfg` template).

Commands (same names, permissions and messages as the original):

| Kind | Names |
| --- | --- |
| console | `mm_ban`, `mm_mute`, `mm_gag`, `mm_silence`, `mm_unban`, `mm_unmute`, `mm_ungag`, `mm_unsilence`, `mm_add_admin`, `mm_remove_admin`, `mm_add_group`, `mm_remove_group`, `mm_admin`, `css_admin`, `mm_as_reload_config`, `mm_as_reload_admin`, `mm_as_reload_punish` |
| chat | `!admin`, `!ban`, `!mute`, `!gag`, `!silence`, `!unban`, `!unmute`, `!ungag`, `!unsilence`, `!add_admin`, `!remove_admin`, `!add_group`, `!remove_group` |
| new | `as_status` (RCON report: per human slot the steamid, admin state, flags, immunity, group and active punishments, plus the prefix/server ids and the pending statement count) |

Flow: `OnPluginStart` reads `core.ini` / `sorting.ini` / `admin_system.phrases.txt`, opens the
database from the `admin_system` section of `databases.cfg` (a missing entry falls back to a local
SQLite file), creates the schema and registers the commands, the core menu items and the s2sdk
listeners. Authentication (or the once-per-second reconcile, which is the reliable path) resets the
slot and loads its punishments and admin record; a ban found there kicks the player
(`NETWORK_DISCONNECT_KICKBANADDED`) immediately, or after `ban_delay` on a forced reload; the
one-second timer expires punishments/rights, announces them like the original and drives the
reconcile. The chat listener captures the typed "own reason" and blocks gags/silences
(`mute_ignore_commands` lets `!`/`/` commands through).

Deviations of the engine side (all deliberate, the rest is parity):

* `mute`/`silence` cannot block *voice*: s2sdk 2.18.2 has no hearing/voice API (the original used
  a `HookIsHearingClient` hook). The punishment is stored, shown in `as_status` and in the menus,
  gag/silence still block chat - the voice part needs the polyhook plugin.
* The reload commands cannot re-open the database (the connection is fixed at plugin start);
  everything else is reloaded.
* The forced reload (`mm_as_reload_punish`) does not print the punishment notices: the original
  passed a database row id where the live path passes a client slot, so its `PrintToChat` could
  address an unrelated player. The kick still happens.
* Argument-count checks follow the documented usage; the original demanded one token more for chat
  calls and removed the last character of the reason (an artifact of the raw chat content).
* `AddPlayerAdmin`'s `expireTime` is a duration in seconds and is stored as an absolute timestamp
  in both the database and the in-memory record (the original stored the raw duration in memory
  for its `bDB = false` path).
